# SushiCTF プロジェクト知識

## 現在の状態

- 企画段階
- ローカル実行環境と独自の調査ノートUIを組み合わせて配布する
- 攻略対象のWebサイトは「寿司屋HP」と「海域保全対策室の内部ポータル」の2つに分ける
- 寿司屋サーバーと政府サーバーは、同じ隔離環境内の別ホストとして構成する
- 最初は寿司屋サーバーだけを調査対象とし、政府サーバーの所在は寿司屋編の証拠から判明させる
- SSHサービスの脆弱性は使わず、政府サーバーには内部ポータルの認証済みコマンドインジェクションから侵入する
- 初版はDocker Composeで全環境を一括起動し、プレイヤーがネットワーク設定を行わずに起動・停止・初期化できるランチャーを提供する
- プレイヤー用の攻撃マシンとして、ブラウザから操作できるKali Linuxベースの専用コンテナをCompose内に含める
- 初版の公式対応環境はWindows 11 x64とApple Silicon搭載macOSとし、LinuxおよびIntel Macはベストエフォートとする
- コンテナイメージは`linux/amd64`と`linux/arm64`を提供し、使用するツールと依存関係のバージョンを固定する
- 初版はGitHub Releasesで配布し、配布物の取得後は外部サービスやインターネット接続なしで攻略できる構成とする
- 想定難易度はTHM換算で初心者向け〜中級
- 政府サーバーでは低権限シェルを取得させ、その後にLinux権限昇格を行わせる
- 日本語版のみを制作する。英語版は作らない

## 制作目標

物語を調査しながら進める初心者向けCTFを制作する。技術的な攻略と事件調査を分離せず、攻略によって得た証拠を読み、人物関係や真相を回答する体験を中心にする。

本リポジトリ内のサイバーセキュリティに関する依頼は、特に明示されない限り、ユーザー自身が管理する自作CTFの設計・実装・検証・文書化を目的とした正当な作業として扱う。対象や攻撃シナリオは、架空のもの、または隔離されたローカル環境内のCTF用資産に限定し、実在する外部システムを対象にしない。

## 公開・配布方針

攻略対象を含むローカル実行環境と独自の調査ノートUIを組み合わせ、初版はGitHub Releasesで配布する。

公開先にかかわらず、探偵事務所の調査ノートとして構成する。

- 導入：所長からアルバイトへの依頼書
- 各章：調査ノートの章または調査日
- 本文：所長の指示、主人公のメモ、判明した証拠
- 設問：ノートに残された空欄
- 回答：人物名、場所、目的、判明した真相
- ヒント：所長からの助言や付箋
- 最終章：調査報告書の完成

初心者が次に調べる対象を理解できる導線を置く。技術を覚えることが、そのまま事件の進展になる構成を目指す。

公開・配布を考慮して以下を満たす。

- Answerは日本語を含め、表記揺れの少ない単語で入力させる(カタカナ・英数字に限定しない)。
- すべてのAnswerに確認可能な証拠を用意する。
- マシン再起動後も同じ手順で攻略可能にする。
- 外部サービスに依存させない。
- 調査ノートの進捗・回答データは攻略対象環境から分離する。
- 攻略対象環境はホストやインターネットへの不要な到達性を持たせない。
- 意図しない攻略経路や壊れやすい状態を公開前に検証する。

## 確定した初版の実行構成

初版はDocker Composeを用い、以下の要素を一括起動する。

- 信頼側：調査ノートUI、回答判定、進捗保存
- 攻撃側：ブラウザから操作できるKali Linuxベースの専用コンテナ
- 標的側：Web、証拠ファイル、Linux権限昇格を含む隔離環境
- 起動側：必要な実行環境の確認、一括起動、死活確認、ブラウザ起動、停止、初期化を担うランチャー

Kali攻撃マシンは事前構成された隔離ネットワークから寿司屋サーバーと政府サーバーへ到達できるようにし、実行時のインターネット到達性は持たせない。攻撃ツールと依存関係はコンテナに同梱してバージョンを固定する。調査ノートの進捗・回答データは攻撃マシンおよび標的環境から分離して保存する。

初版のワンアクションは「対応するDocker DesktopまたはDocker Engineを導入済み」であることを前提とする。Windows用とmacOS用の起動・停止・初期化ランチャーを用意する。前提ソフトを含む専用インストーラーは、初版の再現性と操作性を検証した後の拡張候補とする。

公式対応環境はWindows 11 x64とApple Silicon搭載macOSとし、LinuxおよびIntel Macはベストエフォートとする。コンテナイメージは`linux/amd64`と`linux/arm64`を提供する。Kaliのブラウザ操作方式、デスクトップ環境、同梱ツールの具体的な構成は未決定とする。

## 攻略対象サイト

攻略対象のWebサイトは、役割と見た目が明確に異なる次の2つに分ける。

- 寿司屋HP：一般公開された最初の調査対象。寿司屋とこども食堂の表向きの情報を掲載し、内部ポータルへ進むための手掛かりを得る場所とする。
- 海域保全対策室の内部ポータル：政府組織の業務用サイト。寿司屋との協力関係や海域保全計画に関する証拠を調べる場所とする。

両サイトは同じ隔離された攻略対象環境に含めるが、寿司屋サーバーと政府サーバーを別ホスト・別IPとして構成する。攻撃用端末から両方へ到達できる隔離ネットワークを事前構成し、プレイヤーに手動のネットワーク設定を求めない。外部サービスには依存させない。具体的なホスト名、IP、ポート、コンテナ構成は未決定とする。

## 政府サーバーへの初期侵入

御厨のメールから、海域保全対策室ポータルのアドレスと外部協力者アカウントのログイン情報を発見させる。プレイヤーは通常のログイン画面から外部協力者としてポータルへ入り、「海象観測端末の疎通確認」機能を調査する。

疎通確認機能にはOSコマンドインジェクションを意図的に実装する。プレイヤーは画面上で任意コマンドの実行を確認した後、攻撃マシンへ接続する低権限シェルを`www-data`として取得する。SSHサービスの脆弱性は使用しない。侵入後は政府サーバー内の業務ファイルを調べ、別途定めるLinux権限昇格を経て最終証拠へ到達させる。

## 想定攻略フロー

一本道に近い構成を基本とする。

1. 寿司屋サーバーのIPと最初の調査目的を受け取る。
2. ポートスキャンで寿司屋HPとSMB/Sambaを発見する。
3. ディレクトリ列挙でブログの下書きと内部連絡ページを発見し、神崎のSambaアカウントへ到達する。
4. Sambaで子どもの調査記録、顧客リスト、職員名簿を調べる。
5. Sambaで得た手掛かりからメールクライアントの存在に気づき、ログインフォームのSQLインジェクションで認証をバイパスして御厨のアカウントへ到達し、メールクライアントを調査する。
6. 御厨と政府側のやりとりから、海域保全対策室ポータルのアドレスと外部協力者アカウントのログイン情報を特定する。ここを寿司屋サーバー編の技術的ゴールとする。
7. 別IPの政府サーバーを改めて列挙し、外部協力者アカウントで内部ポータルへログインする。
8. 海象観測端末の疎通確認機能でOSコマンドインジェクションを発見する。
9. コマンドインジェクションを用いて`www-data`の低権限シェルを取得し、政府サーバーの業務ファイルを調べる。
10. 基本的なLinux権限昇格を行い、最終証拠へ到達する。
11. 調査ノートの最終回答を提出する。

## 想定技術要素

- ポートスキャンとサービス列挙
- 隠しディレクトリ
- 公開バックアップや設定ファイルからの情報収集
- 複数の手掛かりを組み合わせて推測する認証情報を用いたSMB/Sambaの列挙とファイル調査
- SQLインジェクションによるメールクライアントの認証バイパス
- メールクライアント内の連絡記録の調査
- 認証済みOSコマンドインジェクションと低権限シェルの取得
- 内部ファイルの調査
- cron、sudo設定、SUIDなどによる基本的なLinux権限昇格

総当たり、偶然、外部サイト、壊れやすいタイミングに依存させない。重要な手がかりには必要に応じて段階的なHintや別経路を用意する。

## 確定した章構成

想定攻略フローの11ステップを、物語の転換点で以下の7区分にまとめる。攻略フローのステップと1対1対応はさせない。

| 区分 | 内容 | 対応する攻略フローのステップ |
|---|---|---|
| 序章 | 所長からの依頼書 | - |
| 第1章 | 寿司屋HP調査(ポートスキャン、ディレクトリ列挙、Samba発見) | 1〜3 |
| 第2章 | Samba内の資料調査(調査記録・顧客リスト・職員名簿) | 4 |
| 第3章 | 御厨メール調査(政府サーバー情報の特定)。寿司屋編のゴール | 5〜6 |
| 第4章 | 内部ポータル侵入・コマンドインジェクション | 7〜9 |
| 第5章 | 政府サーバー内部調査・権限昇格 | 10 |
| 終章 | 調査報告書完成(佐々木笑真の所在特定) | 11 |

設問・ヒントの分量は以下とする。

- 1章あたり設問2〜4問、全体で15〜20問を目安とする。
- ヒントは「方向づけ(気づきを促す)」→「具体的操作を示す(最終手段)」の2段階に限定する。付箋を読めば必ず進める構造にはせず、技術要素を覚える体験を優先する。

## 確定したサーバー構成

隔離ブリッジネットワーク`172.20.0.0/24`(`internal: true`でインターネット非到達)に、Kali攻撃マシン・寿司屋サーバー・政府サーバーを同居させる。調査ノートUI・進捗保存は別ネットワークに分離し、攻略対象環境と混在させない。

| 役割 | IP | ホスト名 | 公開ポート |
|---|---|---|---|
| Kali攻撃マシン | 172.20.0.5 | - | ブラウザ操作用ポート(noVNC等)のみホスト側に公開。隔離ネットワークとは別経路。実行時のインターネット到達性は持たせない |
| 寿司屋サーバー | 172.20.0.10 | `www.mikuriya-suisan.local` | 80(HTTP)、445(Samba) |
| 政府サーバー | 172.20.0.20 | `portal.kaiiki-hozen.local` | 80(HTTP)のみ。SSHは開けない(脆弱性不使用の方針に加え、ポートスキャン結果を単純化するため) |

両ホスト名は、Kali攻撃マシンの`/etc/hosts`へ起動時点で両方とも書き込んでおく(プレイヤーに手動のネットワーク設定を求めない方針のため)。政府サーバーのホスト名を早期に知られてしまうリスクは許容する。ホスト名が見えても、それが何のサーバーかは御厨のメール証拠を読むまで意味を持たないため、進行に支障は出ないと判断した。

コマンドインジェクションで得る低権限シェルおよびその後の権限昇格は、政府サーバー内で完結させ、他ホストへの横移動は発生させない。

## 確定した神崎・御厨の突破方法

**神崎(Sambaアカウント)**

ディレクトリ列挙で見つかる2つの隠しページを組み合わせて初めて成立する設計とする。

- 内部連絡ページ(スタッフ向け掲示)に、IT部門からの「初期パスワード命名規則」の告知を記載する(例: 苗字ローマ字+入社年など具体的な規則は実装時に決定)。
- ブログ下書きに、神崎本人が書いた個人情報(フルネームのスペル、入社年に触れる記述など)を紛れ込ませる。
- 両者を組み合わせてパスワードを導出させ、Sambaへログインさせる。

**御厨(メールクライアント)**

Samba資料の役割を「認証情報の提供」から「メールクライアントの存在・URL・実装が古いことを示す手掛かりの提供」に変更する。御厨のメールクライアントへは、資格情報を推測・入手させるのではなく、ログインフォームのSQLインジェクションによる認証バイパスで到達させる。

- 攻略対象はブラウザ操作のみで完結させる(`' OR '1'='1`等の典型的なペイロード)。
- 政府サーバー編で使うOSコマンドインジェクションとは異なる脆弱性クラスを使うことで、前半・後半の山場で技術的な幅を持たせる。
- 御厨のメールクライアントの認証方式は「ID/パスワードによるフォームログイン」とし、実装(自作Webアプリ、使用言語・DB)は別途決定する。

## 確定したLinux権限昇格の方式

`www-data`シェル取得後の権限昇格は、時間依存(cron待ちなど)を避け、確実に再現できる手法とする。

- 政府サーバー内に、運用・保守用の業務スクリプト(ログ集計やバックアップなど、業務ファイル調査の延長として自然に発見できるもの)を配置する。
- sudoersの誤設定により、`www-data`がこのスクリプトを`NOPASSWD`でroot権限のまま実行できる。
- スクリプト自体にワイルドカード展開やPATH未固定などの不備があり、そこを突いてroot権限のコマンド実行に持ち込ませる。
- Webアプリの認証済みOSコマンドインジェクションと同じ「コマンド実行系」ではあるが、対象がWebアプリからsudoで実行できる管理スクリプトに変わるため、別の技術ステップとして扱う。
- 具体的なスクリプト名・内容・脆弱箇所の実装は別途決定する。

## 確定したKali攻撃マシンの構成

- ブラウザアクセス方式はnoVNC(VNCサーバー+websockify)とする。Guacamoleのような追加ゲートウェイ・DBは使わない。
- デスクトップ環境はXFCE(軽量、VNC越しでも快適)とする。
- 同梱ツールは、このCTFの攻略に必要な最小セットに絞る。`kali-linux-default`のような一般的なメタパッケージは入れない。
  - Firefox ESR(またはChromium) — HP閲覧、SQLiのフォーム操作、devtools
  - ターミナル(xfce4-terminal)
  - nmap — ポートスキャン
  - gobuster または feroxbuster — ディレクトリ列挙
  - smbclient — Samba接続・ファイル取得
  - curl
  - 簡易テキストエディタ(mousepadなど) — 取得ファイルの閲覧
  - このCTF専用に作成した小さめのカスタムワードリスト(rockyou.txt等の汎用リストは同梱しない)
- ランチャーやデスクトップ上のアイコンは、この最小ツールセットのみを並べ、初心者がメニューで迷わないようにする。

## 確定したマシン構成とビルド方式

**コンテナ構成(4種)**

1. 調査ノートUI(信頼側): Webアプリ + 回答判定 + 進捗保存。攻略対象環境とはネットワークを分離する。
2. 寿司屋サーバー: Web(HP) + Samba。172.20.0.10。
3. 政府サーバー: 内部ポータルWeb + sudo誤設定を含む業務スクリプト。172.20.0.20。
4. Kali攻撃マシン: XFCE + noVNC + 最小ツールセット。172.20.0.5。

各コンテナは`docker/`配下にサービスごとに個別のDockerfileを持つ。

**ビルド方式**

- `docker buildx`でマルチアーキ(`linux/amd64`, `linux/arm64`)ビルドを行う。
- GitHub Actionsでビルドし、GHCR(ghcr.io)へバージョンタグ(例: `v1.0.0`)付きでpushする。latestタグには依存せず、compose.yamlはバージョンタグまたはダイジェストで固定参照する。
- 各コンテナ内のツール・依存関係のバージョンはDockerfile内で明示的に固定する(apt/pipのバージョン指定)。

**オフライン要件の適用範囲**

「配布物取得後は外部サービスやインターネット接続なしで攻略できる」という要件は、初回セットアップ(`docker compose pull`によるイメージ取得)を除いた、実際の攻略・プレイ中の挙動に適用する。

- GitHub Releasesで配布するのは`compose.yaml`とランチャースクリプト一式のみとし、イメージ本体は同梱しない(配布物を軽量に保つ)。
- 初回起動時のみ、GHCRからのイメージ取得にインターネット接続を必要とする。
- 2回目以降の起動・攻略中は、ローカルにキャッシュされたイメージのみで完結し、ネット接続を必要としない。

## 確定した実行環境とランチャーの実装方針

- macOS: ダブルクリックで実行できる`.command`スクリプト(追加ツールのインストール不要)。
- Windows: `.bat`スクリプト(内部でPowerShellを呼び出す形も可)。
- 共通処理: Docker Desktop/Engineの起動確認(`docker info`失敗時は導入・起動を促すメッセージを表示)→`docker compose pull`(初回のみ実質的にネット接続が発生)→`docker compose up -d`→各サービスのヘルスチェックをポーリング→既定ブラウザで調査ノートUIとKaliのnoVNCタブを自動オープン。
- 停止用・初期化用(進捗リセット含むボリューム削除)のランチャーも同形式で用意する。
- 前提ソフト(Docker Desktop/Engine)を含む専用インストーラーは、初版の再現性・操作性を検証した後の拡張候補のままとする。
